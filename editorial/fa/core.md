# هسته‌ی تحریریه

قواعد مستقل از پروژه و زمان. وضعیت پروژه، roadmap، feature list، URL محصول، اصطلاحات domain و اطلاعات مشتری اینجا جایی ندارند.

## اصول هسته

### هدف

تولید فارسی‌ای که طبیعی، دقیق، روشن و قابل اعتماد باشد و در عین حال صدای نویسنده را حفظ کند.

### اصول غیرقابل مذاکره

1. **صحت مقدم بر لحن است.** متن خوش‌خوانی که fact را تغییر دهد شکست خورده است.
2. **معنا مقدم بر آرایش است.** ساختار و زیبایی برای روشن‌ترکردن معنا هستند.
3. **مداخله باید متناسب باشد.** proofread را به rewrite تبدیل نکن.
4. **فارسی باید بومی باشد.** ساختار انگلیسی را با واژه‌های فارسی بازسازی نکن.
5. **محدودیت بخشی از حقیقت است.** weakness، uncertainty و tradeoff را برای قوی‌ترشدن copy حذف نکن.
6. **context محلی است.** اطلاعات یک پروژه یا دوره‌ی زمانی را وارد هسته یا task دیگر نکن.
7. **نمونه راهنماست، نه قالب.** عبارت‌های approved corpus را تقلید مکانیکی نکن.
8. **ادعا باید پشتوانه داشته باشد.** صفت‌هایی مثل سریع، امن، کامل، مقیاس‌پذیر و هوشمند بدون سازوکار یا evidence تقویت نشوند.
9. **نویسنده از درون کار حرف می‌زند.** متن نباید مانند Agent بیرونی، PR team یا طرفدار پروژه نوشته شود.
10. **زمان باید صریح باشد.** status، plan، history و current state با هم مخلوط نشوند.

### تعریف کیفیت

```text
Quality = semantic fidelity
        + natural Persian
        + useful structure
        + honest confidence
        + surface fitness
        - generic filler
        - factual inflation
        - temporal ambiguity
        - AI cadence
```

## Transformation contract

### اصل

نوع عملیات تعیین می‌کند چه مقدار اجازه‌ی تغییر وجود دارد.

### عملیات

#### proofread

فقط غلط، نشانه‌گذاری، فاصله و خطای واضح. ساختار و لحن را تغییر نده.

#### light-edit

روانی و ایجاز محدود؛ ترتیب و صدای اصلی حفظ شود.

#### structural-edit

ترتیب بخش‌ها، تکرار و جریان استدلال اصلاح شود؛ facts و stance ثابت بمانند.

#### rewrite

بیان می‌تواند از نو ساخته شود، اما پیام، facts، مالکیت، uncertainty و محدودیت‌ها حفظ شوند.

#### create

از brief و sourceها متن جدید بساز؛ چیزی خارج از evidence اختراع نکن.

#### translate

معنا و جزئیات حفظ شوند؛ ساختار تا حد لازم برای فارسی طبیعی تغییر کند.

#### localize

هدف، audience و effect حفظ شوند؛ wording، مثال و ریتم برای فارسی بازطراحی شود.

#### adapt

یک artifact را برای surface دیگری بازسازی کن؛ copy-paste یا خلاصه‌ی مکانیکی نکن.

#### summarize

اطلاعات کم‌اهمیت حذف شود، نه caveat و شرط حیاتی.

#### expand

فقط با source یا reasoning مجاز گسترش بده؛ fact جدید نساز.

#### audit

مشکل‌ها را مشخص کن و در صورت درخواست replacement بده؛ audit را خودکار به rewrite کامل تبدیل نکن.

### Freeze by default

freeze list در `ENTRYPOINT.md` (مرحله‌ی ۴) پیش‌فرض همه‌ی عملیات‌هاست.

### Scope drift

اگر task «غلط‌گیری» است، متن را marketing copy نکن. اگر task «کوتاه‌کردن» است، نظر نویسنده را تغییر نده. اگر task «دوستانه‌تر» است، اطلاعات جدید اضافه نکن.

## Factual integrity

### قانون

بازنویسی مجوز ساختن اطلاعات نیست.

### انواع گزاره

پیش از نوشتن، گزاره‌ها را در یکی از این دسته‌ها قرار بده:

- verified fact
- source-grounded claim
- author experience
- interpretation
- estimate
- plan
- hypothesis
- unknown

در خروجی، category را بی‌دلیل ارتقا نده.

```text
plan ≠ implemented
implemented ≠ tested
 tested ≠ verified in production
estimate ≠ measured result
opinion ≠ consensus
```

### ادعاهای حساس

برای این موضوعات محافظه‌کارتر باش:

- امنیت و حریم خصوصی
- سلامت و پزشکی
- حقوق و مقررات
- مالی و قیمت
- performance و benchmark
- مالکیت و attribution
- آمار، تعداد کاربر و revenue
- سازگاری، availability و release status

### ادعاهای مطلق

عبارت‌های زیر بدون evidence صریح تقویت نشوند:

- کاملاً امن
- غیرقابل هک
- بدون هیچ خطا
- همیشه
- هرگز
- هیچ داده‌ای ذخیره نمی‌شود
- بهترین یا کامل‌ترین
- صددرصد
- کاملاً ناشناس
- production-ready

ممکن است متن منبع برای ردکردن این ادعاها از آن‌ها استفاده کند؛ negation را به claim مثبت تبدیل نکن.

### attribution

- «من ساختم» فقط وقتی ownership و contribution روشن است.
- «ما ساختیم» فقط وقتی تیم واقعی وجود دارد.
- درباره‌ی کار مشتری، نقش را دقیق بیان کن و مالکیت را حدس نزن.
- quote، testimonial یا تجربه‌ی شخص دیگری را نساز.

### نبود منبع

وقتی اطلاعات کافی نیست:

- claim را محدود کن؛
- uncertainty را آشکار کن؛
- placeholder مشخص بگذار؛
- یا در گزارش نهایی بگو چه چیزی تأیید نشد.

## Temporal integrity

متن باید بداند درباره‌ی چه زمانی حرف می‌زند.

### حالت‌ها

#### timeless

برای اصول، معماری پایدار، راهنما و تعریف. از «الان»، «جدید»، «اخیراً» و «آخرین» بدون مرجع پرهیز کن.

#### current

وضعیت جاری که باید با تاریخ یا نسخه‌ی منبع تأیید شود.

#### historical

رویداد گذشته با تاریخ یا دوره‌ی مشخص.

#### planned

کاری که تصمیم گرفته شده اما هنوز انجام نشده است.

#### event-bound

متنی وابسته به release، کمپین، جلسه یا رویداد مشخص.

### قواعد

- current state را از حافظه یا متن قدیمی حدس نزن.
- «فعلاً» را در سندی که قرار است پایدار بماند حذف یا زمان‌دار کن.
- «نسخه‌ی جدید» را به version مشخص وصل کن.
- plan را با فعل آینده یا status روشن بنویس.
- گزارش تاریخی را با present tense مبهم بازنویسی نکن.
- تاریخ شمسی/میلادی و timezone را در متن حساس مبهم نگذار.

### نمونه

مبهم:

```text
در حال حاضر سیستم از موتور جدید استفاده می‌کند.
```

مرجع پایدار:

```text
سیستم محتوا را با موتور X پردازش می‌کند.
```

گزارش تاریخی:

```text
در بازطراحی نسخه‌ی ۳، موتور X جایگزین مسیر قبلی شد.
```

status report:

```text
وضعیت بررسی‌شده در ۱۱ ژوئیه‌ی ۲۰۲۶: مسیر پردازش بر پایه‌ی X است.
```

## Reasoning و ساختار

صدای خوب فقط انتخاب واژه نیست؛ ترتیب فکر است.

### واحد پایه

```text
مسئله یا مشاهده
→ محدودیت
→ تصمیم
→ دلیل
→ نتیجه
→ مرز یا tradeoff
```

همه‌ی متن‌ها لازم نیست این زنجیره را کامل داشته باشند، اما ترتیب باید قابل دنبال‌کردن باشد.

### شروع متن

از یکی از این‌ها شروع کن:

- یک مشاهده‌ی واقعی؛
- مسئله‌ای که در عمل دیده شده؛
- تصمیمی که نیاز به توضیح دارد؛
- نتیجه‌ای که برخلاف انتظار بوده؛
- سؤال مشخصی که متن پاسخ می‌دهد.

شروع‌های generic مثل «در دنیای امروز» یا تعریف فرهنگ‌نامه‌ای موضوع معمولاً حذف شوند.

### بخش میانی

- فقط اطلاعاتی را نگه دار که تصمیم یا پیام مرکزی را جلو می‌برد.
- feature dump را به capability + reason + effect تبدیل کن.
- وقتی چند راه وجود داشته، گزینه‌ها و معیار انتخاب را کوتاه توضیح بده.
- اصطلاح فنی را برای نشان‌دادن عمق اضافه نکن؛ فقط وقتی برای فهم لازم است.

### پایان

پایان باید یکی از این کارها را انجام دهد:

- نتیجه‌ی روشن بدهد؛
- وضعیت یا مرز فعلی را مشخص کند؛
- تصمیم بعدی را نشان دهد؛
- سؤال باز واقعی باقی بگذارد.

مقدمه را با واژه‌های دیگر تکرار نکن.

### تنوع سطح

- chat: نتیجه و اقدام جلوتر می‌آید.
- UI: عمل و پیامد باید فوری روشن باشد.
- technical reference: تعریف، قرارداد و edge case جلوتر است.
- essay: observation و تغییر مدل ذهنی اهمیت بیشتری دارد.
- report: وضعیت، evidence و تصمیم مقدم است.

## فارسی طبیعی

### معیار اصلی

متن باید طوری خوانده شود که انگار از ابتدا به فارسی فکر شده است، نه اینکه جمله‌ی انگلیسی پس از ترجمه حفظ شده باشد.

### کارهایی که انجام بده

- فاعل تکراری را وقتی روشن است حذف کن.
- فعل را تا حد ممکن طبیعی و نزدیک نگه دار.
- جمله‌های اسمی طولانی را به فعل تبدیل کن.
- از فعل‌های روشن مثل «ساخت»، «تغییر داد»، «بررسی کرد»، «نگه می‌دارد» استفاده کن.
- ترتیب جمله را بر اساس جریان فکر فارسی تنظیم کن.
- اصطلاح فنی جاافتاده را در صورت نیاز انگلیسی نگه دار.
- عبارت انگلیسی را وقتی ترجمه‌اش مصنوعی می‌شود، توضیح کوتاه بده؛ معادل عجیب نساز.

### الگوهای نامطلوب

```text
در راستای بهبود تجربه‌ی کاربری اقدام به پیاده‌سازی...
```

بهتر:

```text
برای ساده‌ترشدن کار با سیستم، این بخش را دوباره طراحی کردم.
```

```text
این امر موجب می‌گردد تا کاربران قادر باشند...
```

بهتر:

```text
با این تغییر، کاربر می‌تواند...
```

```text
سیستم دارای قابلیت انجام پردازش داده‌ها است.
```

بهتر:

```text
سیستم داده‌ها را پردازش می‌کند.
```

### فارسی گفتاری کنترل‌شده

برای chat، UI و متن‌های نزدیک به کاربر، شکل‌های طبیعی مثل «می‌تونی»، «می‌خوای» یا «آماده‌ست» مجازند؛ اما سطح صمیمیت باید از surface و audience بیاید. این شکل‌ها را خودکار وارد مستند فنی یا گزارش رسمی نکن.

### انگلیسی در متن فارسی

English را وقتی نگه دار که:

- نام رسمی API، library، protocol یا command است؛
- معادل فارسی کمتر روشن یا نامأنوس است؛
- مخاطب فنی همان اصطلاح را می‌شناسد.

اما جمله‌ی فارسی را با code-switching بی‌دلیل پر نکن. هر واژه‌ی انگلیسی باید وظیفه داشته باشد.

## قواعد مکانیکی فارسی

### حروف

- `ی` و `ک` فارسی، نه `ي` و `ك` عربی.
- نیم‌فاصله در پیشوند و پسوندهای رایج: `می‌شود`، `نمی‌کند`، `آن‌ها`، `داده‌ها`.
- در identifier، URL، code و quote چیزی را normalize نکن.

### نشانه‌گذاری

- ویرگول فارسی: `،`
- نقطه‌ویرگول فارسی: `؛`
- پرسش فارسی: `؟`
- قبل از نشانه فاصله نگذار.
- بعد از نشانه یک فاصله بگذار، مگر پایان خط یا ساختار code.
- از تکرار `!!!`، `؟؟؟` و ellipsis نمایشی پرهیز کن.

### عدد

- در متن عمومی فارسی، عدد فارسی معمولاً خواناتر است.
- در code، version، path، command، IP، URL، schema و data literal عدد را تغییر نده.
- یک سند باید سیاست عدد ثابتی داشته باشد؛ ترکیب تصادفی نکن.

### تیتر

- تیتر وظیفه‌ی بخش را روشن کند.
- تیتر شاعرانه یا clickbait برای متن فنی نساز.
- nesting بیش از چهار سطح معمولاً نشانه‌ی ساختار ضعیف است.

### پاراگراف

- هر پاراگراف یک وظیفه‌ی اصلی داشته باشد.
- پاراگراف طولانی را فقط وقتی بشکن که جریان استدلال روشن‌تر شود.
- برای هر جمله bullet نساز؛ bullet برای مجموعه‌ی هم‌جنس است.

### Markdown و structured files

دست‌نخورده بمانند مگر task خلافش را بخواهد:

- frontmatter
- fenced code
- inline code
- HTML attributes
- component tags
- table alignment
- placeholders
- translation keys
- JSON keys
- YAML field names
